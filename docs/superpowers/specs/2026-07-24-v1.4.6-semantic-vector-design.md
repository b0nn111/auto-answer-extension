# 1.4.6 Semantic Vector Retrieval Design

## Goal

Improve local material retrieval when the question and reference use different wording or mixed Chinese/English phrasing, while keeping the feature fully local and small enough for a browser extension.

## Scope

This update adds a lightweight local semantic-vector layer for uploaded materials. It does not add a neural embedding model, HNSW, sqlite-vec, a remote vector database, account login, or cloud sync.

## Architecture

- `semantic-vector.js` creates fixed-size hashed vectors from lexical tokens and bilingual concept cues.
- `material-db.js` stores a vector on newly imported material chunks.
- `material-retriever.js` computes a query vector and combines lexical, phrase, and semantic scores.
- Existing `local-ranker.js` and `material-answerer.js` continue to decide whether a retrieved chunk is strong enough to become a reference answer.

## Data Flow

On import, each material chunk stores extracted text, Markdown, citation metadata, and an optional semantic vector. Existing chunks remain valid; if a chunk has no vector, retrieval computes one on demand.

On question detection, retrieval builds the existing keyword query plus a semantic query vector. Candidate chunks receive `lexicalScore`, `semanticScore`, and combined `score`. The service worker logs these values for diagnostics.

## Guardrails

Pure semantic matches must pass a higher threshold before they are returned. This prevents broad concepts such as fruit, color, or item from pulling unrelated documents into the answer pipeline.

## Testing

Regression tests cover:

- Existing alias-based material retrieval.
- No hard-coded fruit bias.
- Semantic vector recall for Chinese question text matching English reference text.
- Existing 1.4.5 material fallback, diagnostics, annotation, and parser behavior.
